## 점검 후 실행 순서

1. 17시 이후 실제 서버 점검 종료 및 현재 앱 화면 확인. 연장 중에는 입력/로그인 반복 금지.
2. 의뢰 최신 이름 분류/동일성 수정의 신규 출항, 연구 누적 수령/대기열 확인.
   10:49 이전 성공과 최신 코드 실기를 혼동하지 않는다.
3. **대형작전 일일·좌표·요새·보스의 개별 기능**을 우선 확인한다. 개척만 반복하며
   이들을 모두 개척 완료 대기로 두지 않는다. `is_in_opsi_explore()`는 게임 해금이
   아니라 Enable/NextRun 기반 스케줄 조건이다. 독립 검증 동안 필요하면 Alas.exe
   UI로 개척을 일시 비활성화하되 LastZone=72와 실제 진행을 바꾸지 않고, 종료 후
   활성 상태를 복원한다. 이것을 개척 완료로 기록하지 않는다.
4. AP/좌표/적응도/현재 함대 조건을 먼저 확인한다. AP 구매 상한1은 유지하고
   추가 유료 구매나 보호 제한 완화는 하지 않는다. 한 작업이 조건 부족이면
   실제 원인을 기록하고 다른 독립 작업을 확인한다. ForceRun을 무작정 켜지 않는다.
5. SP는 원래 편성 복원 정보가 오면 검증한다. 정보 없이 다른 함대를 임의로
   구성하거나 기존 제1함대가 원복됐다고 추정하지 않는다.
   단, 점검으로 기존 이벤트가 종료될 가능성이 확인됐다. 먼저 해당 이벤트의
   실제 개방 여부부터 확인하고, 종료됐으면 복원만 기다리며 재진입하지 않는다.
6. 20시 보고는 `실기 확인`, `수정/오프라인만 확인`, `조건 미충족`, `유료/범위 제외`를
   구분한다. 메뉴 전체나 모든 이벤트/상품/상황을 검증했다는 백분율을 만들지 않는다.

## 오프라인 감사에서 확인한 대형작전 제약

- `module/os/tasks/explore.py`는 개척 중 다른 OS 작업 예약을 뒤로 미룬다.
- `module/os_handler/mission.py:is_in_opsi_explore`는 스케줄 상태 판정이다.
- `archive.py`, `month_boss.py`, `meowfficer_farming.py`는 이 상태에 따라 조기 종료한다.
- `daily.py`는 개척 중 항구 임무 경로가 달라진다. `obscure.py`의 ForceRun=false는
  한 좌표 처리 후 반환하지만 abyssal/stronghold는 반복하면서 작업 전환을 검사한다.
- `module/campaign/os_run.py`는 AP 부족 예외를 예약 연기로 처리한다. 이 경우의
  End task 로그는 전투 성공 근거가 아니다. 월간 보스 적응도 검사는 유지한다.

22개 통과했다. 운영 코드를 변경하거나 게임을 실행하지 않았다.
이는 이미지 인식·좌표 사용·실제 전투·실제 구매 성공의 증거가 아니다.

  155개였다. 모두 파일을 읽을 수 있고 인식 영역이 이미지 크기 이내였다.
- 이는 Template 클래스·동적 Button 전부의 검사도, 현재 게임 화면의 일치율도
  아니다. 특히 fallback 이미지가 한국어 화면에 맞는다고 입증하지 않는다.
  실제 대형작전 좌표/요새/보스 화면의 한국어 차이는 점검 후 확인해야 한다.

  이미지 선택 정책을 이번 감사에서 변경하지 않았다.

## 점검 중: 창고 아이템 재선택 반복 방지 (오프라인 수정)

- `_storage_item_use`는 정보창(GET_MISSION)이 3회 나타나면 정상 반환했지만,
  로그/샘플 사용 바깥 반복문은 같은 템플릿을 다시 찾아 사용을 재시도할 수 있었다.
  실제 성공이 확인되지 않은 상태를 바깥 반복으로 돌려보내는 경로를 검사에서 재현했다.
- KR에서는 세 번째 정보창을 닫은 현재 화면을 로컬 진단 파일에 저장하고
  RequestHumanTakeover로 중단한다. 다른 서버의 기존 재인식 동작은 유지한다.
  성공한 사용을 취소하거나 좌표 인식 임계값을 낮추지 않았다.
- 실패 검사 후 수정, 전체 152검사 통과. 이 상황의 실제 계정 재발은 아직
  관찰하지 않았다. 점검 후 실기에서 해당 진단이 나오면 아이템 템플릿/화면을
  수정해야 하며, 단순 중단을 아이템 사용 기능 완료로 처리하지 않는다.

  실패 뒤 False를 반환해도 창고/지도 호출부는 확인 없이 globe_enter로 진행했다.
- 두 상황을 실패 검사로 재현했다. KR에서는 요청 종류가 없거나 선택 확인을
  3회 실패하면 현재 프레임을 로컬에 저장하고 RequestHumanTakeover로 중단한다.
  요청 종류가 실제 선택된 정상 경로와 일본 서버의 기존 fallback도 검사했다.
- 전체 156검사 통과. 이는 오진입 차단 수정이며, 한국 서버의 해당 특수 해역
  인식/출입/클리어를 통과한 것은 아니다. 점검 후 진단이 발생하면 실제 화면으로
  이미지 인식 문제를 수정하고 다시 검증한다. 게임 입력은 계속 중지 상태다.

## 점검 중: 행동력 구매 선택 확인 누락 수정

- 연료 구매 전에 `action_point_set_button(0)`가 실패해도 반환값을 무시하고
  구매 횟수/잔액 검사 후 사용 버튼을 누르는 경로를 실패 검사로 재현했다.
  KR에서는 연료 선택 미확인 시 로컬 진단을 저장하고 사용 전에 중단한다.
- 정상 연료 선택 후 기존 구매 경로와 주간 상한 차단은 유지하며 함께 검사했다.
  전체 159검사 통과. 실제 구매를 새로 실행하지 않았고 상한 1도 변경하지 않았다.
- 좌표 처리의 `globe_enter(zone=72)`는 화면 이동 좌표를 새로 선택하는 함수가
  아니며 이미 고정된 해역에 진입한다. 72의 위험도 6은 AP 비용 계산에 전달된다.
  이 숫자만 보고 실제 해역을 72로 잘못 이동한다고 단정하지 않았다.

## 점검 중: 보유 행동력 아이템 선택 확인 보완

- 보유 AP 아이템도 선택 전환 실패를 무시하고 사용했으며, 활성 표시 미인식 시
  첫 번째 20 AP 상자를 선택된 것으로 가정했다. 두 경로를 실패 검사로 재현했다.
- KR 활성 표시 미확인은 -1로 반환해 실제 클릭/확인을 시도하게 하고,
  2초 선택 전환이 끝내 실패하면 진단 저장 후 사용 전에 중단한다.
  확인된 상자의 사용 및 AP 증가 후 정상 종료, 다른 서버 기존 동작도 검사했다.
- 전체 164검사 통과. 실제 AP 아이템이나 연료를 소비하지 않았고 한국 서버
  실제 선택 표시의 인식 정확성은 점검 후 재검증이 필요하다.

## 점검 중: 요새 전투 실패 반환값 누락 수정

- `run_stronghold`가 모든 함대의 실패 뒤 False를 반환해도 호출부가 무시하고
  수리/상태 해소 후 바깥 요새 반복으로 돌아가는 경로를 실패 검사로 재현했다.
- 기존 함수에 명시된 예외 계약 및 심연 처리와 같이 RequestHumanTakeover로
  중단하도록 수정했다. 성공한 요새의 수리/상태 해소 경로는 유지한다.
  공통 호출부의 반환값 누락이므로 한국 서버에만 국한된 변경은 아니다.
- 실패 시 재시도 루프에 도달하지 않는 검사와 성공 후처리 검사 포함 전체
  166개 통과. 실제 요새의 진입·전투·완료 화면 인식은 여전히 점검 후 대상이며,
  이 중단 보완을 요새 클리어 실기 성공으로 기록하지 않는다.

## 점검 중: 월간 보스 조건과 건너뜀 기록

- 일반 난이도만 설정하고 어려움 보스를 발견한 경우, 전투 없이도
  `month_boss_delay(is_normal=False, result=True)`를 호출해 어려움 클리어 로그를
  남겼다. 실패 검사로 확인 후 같은 월초 예약을 직접 설정하도록 수정했다.
  이제 이 분기는 건너뜀 로그만 남기며 전투 성공으로 기록하지 않는다.
- 개척 예약 활성 시 조기 종료, 보스 미발견 시 전투 금지, 적응도 세 항목 중
  하나라도 203/203/156 미만이면 진입 금지, 경계값 충족 시 실제 전투 결과 전달을
  포함한 5개 모의 검사를 추가했다. 전체 171개 통과했다.
- 적응도 임계값과 난이도 설정은 바꾸지 않았다. 현재 계정의 보스 난이도와
  실제 OCR/전투 결과는 점검 후 확인하며, 모의 경계값 검사를 실기로 세지 않는다.

## 점검 중: 실제 모듈 로딩 검사

- 기존 AST 추출 검사와 별도로 새 Python 프로세스에서 서버를 KR로 지정하고

- 다중 상속 후 요새/월간 보스/행동력 메서드가 수정한 함수에 연결되는지 확인하고,
  모의 UI 객체를 넘겨 실제 RequestHumanTakeover 예외로 연료 선택 실패와
  요새 전투 실패가 중단되는지 검사했다. 이때 사용/수리 후처리는 호출되지 않았다.

## 점검 중: 개발 도크 수량 조절과 실행 조건

- 감소 시 `multi_click(n=diff)`에 음수를 넘겨 실제 감소 클릭이 없었고,
  목표보다 많은 현재 수량을 음수 잔여량으로 반환해 확인으로 진행할 수 있었다.
  마지막 조절 클릭 뒤 재확인도 누락됐다. 실패 검사로 세 경로를 재현했다.
- 감소 클릭은 절댓값 횟수로 수행하고 세 번의 조절 뒤에도 다시 수량을 읽는다.
  음수 OCR 또는 목표 초과가 남으면 None을 반환해 구매/보유 도면 사용 확인을
  막는다. 목표 이하 일부 수량은 기존대로 실제 잔여량을 반환한다.
- 수량 및 구매/사용 호출부의 확인 금지 포함 6개 장치 없는 검사 통과.
  한국어 버튼/OCR 인식이나 실제 강화 성공을 검증한 것은 아니다.
- 현재 개발 도크 비활성, PR/DR 대상 인덱스 모두 0으로 미지정이다. 설정을
  변경하지 않았다. `shipyard_run`은 구매 전 `_shipyard_use`에서 보유 도면을
  먼저 사용하므로 BuyAmount=2를 전체 도면 소비 상한 2로 해석하면 안 된다.
  점검 후 실제 대상 함선과 보유 도면 사용 범위를 확인한 뒤 실행해야 한다.

- 후속 검사에서 세 번 조절 후에도 선택 수량이 0이면 원래 요청량 전체를
  잔여량으로 반환해 0개 확인과 같은 수량 재시도가 가능함을 확인했다.
  실제 선택이 없는 경우도 None을 반환하도록 보완했다. 구매/보유 도면 사용
  양쪽에서 확인과 비용 처리를 호출하지 않는 검사 포함 전체 180개 통과.
  정상적인 일부 수량 선택은 유지하며, 실제 한국 서버 도크는 아직 실행하지 않았다.
